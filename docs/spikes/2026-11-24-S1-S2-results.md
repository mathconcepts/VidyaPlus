# Spikes S1 and S2: what could be verified without a browser or an LLM (24-26 Nov 2026)

Same stack and rules as the S3 doc: pinned DeepTutor 1.7.3 container, synthetic accounts only, no LLM key.
Reproduce: `SUDO=sudo vidhya/sync/integration/run-all.sh` (checks in `s3_checks.py` for S1, `s2_checks.py`, `s2_tool_view.py`, `session-contract.itest.ts`).

## S1: `/exam` session via `dt_token` -> `/api/auth/status`

Plan pass criterion: "yes on a phone at 360 px; an expired cookie redirects to login". **Only the server contract part could be verified here.**

|---|---|---|---|

| S1-b | PASS | no cookie -> authenticated=false, user_id=null (brain answers SessionMissing) | HTTP 200; {'enabled': True, 'authenticated': False, 'user_id': None, 'username': None, 'role': None, 'is_admin': False, 'avatar': '', 'preset': None, 'learning_policy': None} |
| S1-c | PASS | garbage and tampered cookies -> authenticated=false (an expired/invalid cookie redirects to login) | garbage=False, tampered=False |
| S1-d | PASS | cookie attributes the brain and Caddy rely on: name dt_token, HttpOnly, Path=/, SameSite=lax | Set-Cookie attrs: HttpOnly; Max-Age=86400; Path=/; SameSite=lax  (Secure is absent here: cookie_secure=false in auth.json; production must set it true behind TLS) |
| S1-e | PASS | the token carries exp (24 h default) and uid; the user id the brain gets from /status equals the JWT uid | exp-iat=86400s; uid==user_id: True |

Also PASS: `vidhya/sync/integration/session-contract.itest.ts` runs the brain's real `makeSessionResolver` against the live DeepTutor: a real `dt_token` maps to the enrolled student; no cookie and a tampered token give `SessionMissing`; an unregistered account gives `UnknownStudent`; an unreachable DeepTutor gives `AuthUpstreamUnavailable` (4 tests).

**Not verified (S1):**
- `/exam` behind Caddy on the DeepTutor domain (no Caddy in this stack): that the browser sends `dt_token` to `/exam/api` on the same site.
- KaTeX at 360 px on a phone (out of scope for this run).
- An *expired* (rather than invalid) token: the 24 h `exp` is in the JWT (S1-e), but expiry was not waited out. Invalid and tampered tokens are rejected as `authenticated: false`.
- `Secure` cookie flag: absent in this test stack (`cookie_secure=false` in `auth.json`); production must set it and serve over TLS.
- `must_change_password` accounts: the flag is returned by login; how the brain should treat a student who has not yet changed a password was not decided.

## S2: a brain MCP server granted via `grants.mcp_tools` shows up for a standard student

Plan pass criterion: "the tutor calls `explain_receipt` in a real chat". **Verified at the layer that decides visibility and execution; the model-driven call in a real chat is NOT verified (no LLM key).**

Method: a stand-in MCP server (`mock_brain_mcp.py`, stdio, synthetic tools named like plan X1) is registered in the deployment registry through DeepTutor's admin API; then DeepTutor's own `build_tool_view` (the function a tutor turn runs before the model is called, in `deeptutor/runtime/providers/view.py`) is run in the container as each student against the real MCP manager and the real `settings/mcp.json`.

### Code path (read from upstream, 1.7.3)

`multi_user/tool_access.py:allowed_mcp_tools` reads `grant.mcp_tools` (admins unrestricted; a non-admin whose grant omits it gets an empty set) -> `runtime/providers/view.py:_user_grant` -> `authorize.py:authorize_mcp_tools` -> `build_tool_view` keeps only granted names in the pool, the deferred-tool manifest and the scoped registry; a dispatch of any other name is refused with "This tool is not available in this conversation". Tool names are `mcp_<server>_<tool>`, exactly as the plan's grants assume.

### Findings for the brain's MCP wiring

- **S2 passes at tool-view level for a standard student.** If it holds in a real chat, `mcp_vidhya_*` grants applied per student by `vidhya tier set` (PUT `/api/multi-user/users/{id}/grants`) are enough; no plugin is needed.
- **Admin registry URL rules (R3):** private and loopback `http` URLs and a static `Authorization` header are accepted for an administrator, but a hostname must resolve at save time. Register the brain only once its container is up (compose DNS name resolves) or use its IP.
- **Students cannot widen their own surface:** they cannot edit `/api/settings/mcp` or their own grants (403); their self-service MCP servers must be public remote URLs (no stdio, no loopback/private) and are authorised by ownership, outside the grant. The brain's tools are identity-free (plan X1) so a student-owned public server gains nothing from them.
- The MCP tool call shown is **synthetic**; "never returns values" for `explain_receipt` is a brain contract test, not something this spike can show.

**Not verified (S2):** the LLM choosing to call `explain_receipt` in a live tutor chat; MCP over streamableHttp with the real bearer header against the real brain `/mcp` (the stand-in is stdio; only config acceptance of URL + header was checked); behaviour when the brain is down mid-chat.
