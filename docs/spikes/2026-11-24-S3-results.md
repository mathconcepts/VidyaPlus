Run by `vidhya/sync/integration/s3_checks.py` (checks S1 and S3 and the S-sync integration test) against the pinned DeepTutor
container (`vidhya/sync/integration/docker-compose.yml`, image digest `sha256:dff6d6ef...`; its `/app/deeptutor` tree was verified
byte-identical to `upstream/deeptutor/deeptutor`). One synthetic test student (`it-student-1`), synthetic items only ("What is 2+2?").

## Findings that change the plan or the build

- **F1 (d), plan §11:** `GET /api/question-notebook/practice/questions/{id}` and `/queue` return `entry.correct_answer` and `explanation` to the signed-in student before any attempt. DeepTutor hides the key only in its UI. Synced practice-pool MCQ/MSQ keys are therefore readable by any logged-in student calling the API. Acceptable only because mock-pool and NAT items never sync (plan §3); §11 should say so.
- **F2 (R9 detail):** the trigger bumps `practice_review_state.version` only when `question`, `options_json` or `correct_answer` change and only when a review-state row exists. Explanation-only changes do not bump the version (checked: S3-g4). The applier re-stamps the tag and keeps the version.
- **F3 (g):** `question_id` is NOT unique on its own. The unique index is `(origin_type, origin_ref, turn_id, question_id)`. Our rows live in their own namespace (`origin_type=external_import`, `origin_ref=vidhya-sync`), so a student's own imports (`practice-import`) can never collide with or be touched by sync.
- **F4 (found during the run):** an applier running as root creates a student's store directory root-owned and DeepTutor (uid 1000) then answers `500 PermissionError` for that student. The applier now refuses to run as root, and `vidhya sync` runs it with `docker exec -u deeptutor`. Production runbook: never run the applier as root.
- **F5:** `must_change_password: true` is set on admin-created accounts and does not block the practice API.
- **F6:** a forced kill (`os._exit(137)` inside the transaction, the SIGKILL equivalent) leaves the bank untouched (SQLite journal rollback) and the `flock` is released by the OS; the re-run completes.
- **F7 (R20):** events reach `events.jsonl` before the delete and before commit, deduplicated on DeepTutor's `request_id`; a rolled-back run, a killed run and the real run produce one line, not three.

## Not verified / limits

- One student. Concurrency across many students and a bank of ~450 items was not load-tested (the fixtures have 8 items).
- The synthetic `/v1/servable` is a JSON fixture; the real HTTP route is built on another branch. The assumed body is `{pack_version, items: Item[]}` (documented in `vidhya/sync/src/types.ts`). Whoever builds it must match that or change the interface.
- The kill test simulates SIGKILL with `os._exit(137)` at a fault point inside the transaction (`VIDHYA_SYNC_TEST_FAULT`, test hook only); a real `docker kill` of the whole container mid-write was not run.
- `SyncLockTimeout` was exercised with a second writer holding `BEGIN IMMEDIATE`; DeepTutor's own writers were not involved.
- WAL checkpoint behaviour under a running DeepTutor with an open browser session was not observed.
