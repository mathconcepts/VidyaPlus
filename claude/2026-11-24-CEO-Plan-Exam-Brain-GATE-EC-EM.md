**Ownership.** The pack owns what's true. The brain owns marks, plans and disputes. DeepTutor owns the experience shell, practice, tutor and memory. The pack never imports DeepTutor code. The brain reads the pack only through its release artifact (`dist/<version>/`), so content stays independent of the software and in sync through versioned releases.

**Live status overlay (one rule for "what is servable now").** A release is immutable. Between releases, the brain keeps a **status overlay** (`item_status` table: `item_id, fingerprint, status ∈ disputed/quarantined, since, reason`).

**Servable set** = release items with `status: verified` **minus** overlay entries matching that fingerprint. Everything that serves or syncs reads `GET /v1/servable?pool=…`, never the raw release: sync, the drift check, the planner, the mock and the tutor tools.

A patch release folds the overlay back into the pack (each item re-cleared or retired), and the folded overlay rows are then closed.

**Pools.** Every item has `pool ∈ practice / mock / diagnostic`. Pools are disjoint, which is a K2 gate.
- Practice-pool MCQ/MSQ items go to DeepTutor via sync.
- Practice-pool NAT items are served only by the brain.
- Mock-pool items are served only inside a mock.
- Diagnostic-pool items are the public free sample.

**Identity (R1, R7).** Every `/exam/api` request carries DeepTutor's `dt_token` cookie (same site, httponly). The brain forwards it to `GET /api/auth/status` over loopback, caches the result for 60 s, and maps `user_id` → `student_id` through the registry (v5 P4). **No handler accepts a student id from a request body or from MCP arguments.** MCP tools are identity-free. The brain's MCP endpoint is bound to the DeepTutor↔brain docker network. The code-execution runner sits on a separate network with no route to the brain.

- an MCQ key is outside its options
- an MSQ item has fewer than 2 correct options
- **any MCQ/MSQ distractor is mathematically equal to a key** (SymPy `simplify(option − key) == 0`, or numeric equality within tolerance), per O4

- a section or type count is below the floor (§5). **This floor gate runs only with `pack build --release 1.x`.** Pre-1.0 builds (`0.x`, which W0 uses for the cohort's starting MCQ/MSQ pack) run every integrity gate above, but not the floors.

**Taxonomy**, applied in this order:
1. `TIME` (unattempted at time-out)
2. `EXAMCRAFT` (a wrong answer given in under 0.3 × the item's median time, or under 0.3 × the prior minutes before B7 data; i.e. a guess)
3. `CALC` (chose a distractor tagged `calc`)
4. `CONCEPT` (chose a distractor tagged `concept`, or a wrong NAT value outside the near band)
5. `UNCLASSIFIED`

| S-sync | `vidhya sync [--student] [--to <version>] [--dry-run]` (`vidhya/sync/`, R2) | Runs inside the DeepTutor container (`docker exec`) using DeepTutor's own pinned store code, under a `flock` on `/data/vidhya/sync.lock` (a second run exits `SyncAlreadyRunning`). 1. copy every `practice_review_events` row for the ids about to be deleted into `events.jsonl` (deletes cascade, SF5);
2. delete changed and removed ids. A change in explanation only keeps the same DeepTutor id (SF6), so it's delete and insert too;
3. insert new rows;
4. commit;
5. verify counts.

Guards:
- lock wait >5 s → `SyncLockTimeout`, the student is skipped and retried next run;
- >20% of a bank removed → `SyncMassRemoveRefused` unless `--allow-mass-remove`;
- the store schema ≠ the pinned version → `StoreSchemaMismatch`, the whole run aborts before any write.

A rolled-back transaction leaves the bank exactly as it was. Idempotent. Runs nightly, on release, and hourly while an overlay dispute is open. |
| S-drift | Drift check | After each sync, per student: DeepTutor items not in the servable set = 0, and servable MCQ/MSQ items not in DeepTutor = 0. Non-zero means an alert and a re-run. |
| v5 | P2 ledger-sync, P3 LLM gateway (hard cap), P4 registry, C2 host, C4 enroll, L1–L5 | Unchanged; the brain joins the compose file, backups and uptime check |

### Section 1: Architecture Review
**CRITICAL GAP (R1).** D4's "thin Python plugin with routes, tools and an Exam page" can't work as specified:
- SF1 means a plugin route can't tell the brain which student is calling.
- SF2 means the Exam page can't reach the brain at all.
- SF3 means the plugin's tutor tools never appear in chat.

The §8 fallback (a standalone `/exam` served by the brain) becomes the primary path.

**Proposed architecture (R1 option A):**
```
 Browser (student) ── https://app.<domain>/ ──► Caddy
   │  cookie dt_token (httponly, same site)            ├─ /            → DeepTutor web + API (pristine + branding)
   │                                                   ├─ /exam/*      → vidhya/brain static Exam app
   └───────────────────────────────────────────────────└─ /exam/api/*  → vidhya/brain HTTP /v1 (session check)
                                                                         │ GET /api/auth/status (forward cookie, 60 s cache)
                                                                         ▼
                                                                      DeepTutor (loopback)
 DeepTutor tutor chat ── MCP (granted per student via grants.mcp_tools, like Wolfram) ──► brain MCP (identity-free tools)
 vidhya sync (docker exec in the DeepTutor container, DeepTutor's own store code) ◄── brain /v1/servable
 code-exec runner sidecar (SymPy, L3): separate docker network, no route to brain
```
- **Dependency graph:**
  - pack `dist/` → brain (read-only)
  - brain → DeepTutor `/api/auth/status` (read-only)
  - sync → brain (read) and → DeepTutor store (write)
  - DeepTutor → brain MCP (read and dispute-write only)
  - No cycles. DeepTutor never imports Vidhya code.
- **Coupling, before → after:**
  - **Before:** brain ← plugin ← DeepTutor plugin host, with identity smuggled through.
  - **After:** brain ← Caddy path + one stable DeepTutor endpoint (`/api/auth/status`), plus MCP.
  - The new coupling is on `/api/auth/status` response shape and the cookie name `dt_token`. It's pinned by a contract test that runs on every `sync-deeptutor.sh` upgrade.
- **Rungs:**
  - The Exam app is a **standalone** service, the same rung as the funnel. PORTING gets a row for it.
  - Tutor tools use rung 1 (configuration): an MCP server is granted per student.
  - No patch is needed.
- **Scaling:**
  - At 10× (200 students), still one box.
  - At 100×, the per-request auth check is the first pressure point, mitigated by a 60 s token cache.
  - After that comes Wolfram quota, which only matters to K3/K4 offline.
  - Sync is O(students × changed items).
- **Single points of failure:**
  - **The VPS.** Mitigated by backups and the restore drill.
  - **Brain down.** The Exam tab shows a banner while practice and tutor keep working.
  - **DeepTutor auth down.** The Exam tab can't authenticate and shows "sign in on the main app".
- **Security architecture.** See Section 3.
- **Rollback.** Caddy route `/exam` off, plus `mcp_tools` revoked in the tier template. DeepTutor is untouched. Under 5 min.
- **Value test.** `counts.md`, the drift check and the daily ops line all feed decisions (K3 sizing, alerts, the SSOT). Nothing is a meta-artifact.
- **Accepted cherry-picks:**
  - D6.6 (Today card) lives in `/exam`.
  - D6.1 (disputes) works from `/exam` (identified; 2-reporter quorum, O2) and from tutor MCP (anonymous; Giri's queue only).

### Section 4: Data Flow & Interaction Edge Cases
```
ANSWER (/exam)  INPUT(response, item_id) → VALIDATE(session, servable, pool, type) → GRADE(scorer, exam.yaml)
                → PERSIST(attempt + fingerprint, pack_version, idempotency key) → OUTPUT(correct, marks, reveal)
  nil/empty: NatParseError / unattempted · wrong type: 400 · too long (>64 chars NAT): 400
  timeout/OOM: none (pure fn) · dup: idempotency key returns first result · stale: pack_version mismatch → "Content updated"
SYNC            servable(brain) → diff per student → [BEGIN IMMEDIATE] delete changed/removed ids, insert new rows
                with tags ledger:<id>@<fp8> [COMMIT] → verify counts → drift
  brain down: abort before write · lock: SyncLockTimeout · schema: StoreSchemaMismatch · mass remove: refused
  explanation-only change (same DeepTutor id, SF6): handled by delete+insert inside one txn (R2)
FACTORY (K3)    candidate → LLM draft → schema check → SymPy script → Wolfram (separate pass) → agree? → verified
  malformed/empty/refusal/schema: stays candidate · engine error ≠ disagree · encoding: LaTeX normalised before fingerprint
```
**Async ordering.** The invariant: *no student practice attempt is lost, and no student ever sees a withdrawn item after the sync that withdraws it commits.*

**Schedule A (sync vs a live review).**
```
time   sync(student S)                          S answers item X (DeepTutor)           shared: practice.db
t0     ledger-sync S (reads events ≤ t0)
t1                                               POST review X → BEGIN IMMEDIATE ...  event e1 written
t2     BEGIN IMMEDIATE (waits for S's txn)                                             lock held by S
t3     delete X (cascade deletes e1!)                                                  e1 gone, never captured
```
**Order A loses e1.** The mechanism that fixes it (R2): inside the sync transaction, *before* deleting, read and append to `events.jsonl` every `practice_review_events` row for the ids about to be deleted. One transaction holds the lock, so both orders are safe:
- If S's review commits first, the event is read inside the sync transaction before the delete.
- If sync commits first, S's review hits a missing entry and returns DeepTutor's own 404 ("question removed"), and nothing is written.

The "skip students active in the last 2 min" rule is dropped; the transaction replaces it.

**Schedule B (two sync runs: nightly + dispute hourly).** A `flock` on `/data/vidhya/sync.lock` serialises them, and the second run exits `SyncAlreadyRunning`.

**Schedule C (dispute vs mock in progress).** An item disputed mid-mock stays in that attempt, because the form is frozen at start, and it's scored as "withdrawn: not counted" on both sides of the marks.

**Regression proof:** a pause-point test runs sync and review in both orders on a real SQLite file. Expected: the event is in `events.jsonl` either way.

### Section 7: Performance
- Indexes: `attempts(student_hash, ts)`, `attempts(item_id, fingerprint)`, `item_status(item_id)`, `disputes(item_id, day)`.
- No N+1: the planner loads servable items and stats once per request (about 450 rows).
- Memory: the servable set is about 450 items × 2 KB ≈ 1 MB, cached per `pack_version`.
- Slowest paths:
  - The marks-range bootstrap (1,000 resamples × ≤300 attempts) is about 20 ms. It's cached per student until the next attempt.
  - Sync per student is about 0.2 s.
  - The session check costs one loopback call and is cached 60 s.
- Background jobs:
  - K4 makes about 420 Wolfram calls in batches of 20 with backoff. Worst case is a few hours, and it's resumable.
  - Calibration runs nightly over about 10k attempts in under 1 s.
- Connection pressure: a single SQLite writer, with WAL readers.

No issues beyond the indexes, which are now part of B3.
